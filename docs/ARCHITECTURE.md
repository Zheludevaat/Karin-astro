# Target architecture

The existing `index.html` is a working prototype and reference implementation. It is not the desired long-term architecture.

The Lovable rebuild should separate presentation, state, data, and generated astrology assets.

## Recommended application shape

Use the current framework generated by Lovable for a new project. Do not force the legacy project into the old static structure.

A target structure should resemble:

```text
src/
├── components/
│   ├── AstrologyChart.tsx
│   ├── DiscoveryDialog.tsx
│   ├── DiscoveryProgress.tsx
│   ├── Starfield.tsx
│   └── SummaryCard.tsx
├── data/
│   ├── karinProfile.ts
│   └── signs.ts
├── hooks/
│   └── useDiscoveryProgress.ts
├── lib/
│   ├── chartGeometry.ts
│   ├── sharing.ts
│   └── storage.ts
├── routes/
│   └── index.tsx
└── styles/
    └── app.css

public/
├── charts/
│   └── karin-chart.svg
└── app-icon.svg
```

Exact framework-generated filenames may differ. Preserve the responsibilities even if Lovable chooses a slightly different folder convention.

## Component responsibilities

### AstrologyChart

- renders the supplied chart SVG
- creates or renders accessible interactive hotspots
- converts planet placement data into chart geometry only when needed
- emits semantic discovery events
- contains no interpretation copy

### DiscoveryDialog

- presents a planet or aspect interpretation
- has keyboard-accessible close controls
- uses proper dialog semantics
- does not mutate astrology data

### DiscoveryProgress

- shows how many discoveries have been completed
- handles the minimum-discovery threshold for the summary CTA
- should not know how the chart is drawn

### SummaryCard

- composes a summary from discovered items
- supports Web Share where available
- includes a graceful fallback

### Starfield

- owns the decorative canvas animation
- respects reduced-motion preferences
- never blocks interaction

## Data model

Use typed data. At minimum:

```ts
export type PlanetKey =
  | 'Sun'
  | 'Moon'
  | 'Mercury'
  | 'Venus'
  | 'Mars'
  | 'Jupiter'
  | 'Saturn'
  | 'Uranus'
  | 'Neptune'
  | 'Pluto'

export interface PlanetInterpretation {
  icon: string
  sign: string
  degree: string
  house: number
  element: string
  germanName: string
  title: string
  subtitle: string
  text: string
  tip: string
}
```

Do not spread sign maps, display strings, and chart constants through components.

## State

The only persistent browser state required for the existing product is discovery progress.

Use a small versioned storage key, for example:

```text
karin-astro:discovery:v1
```

Store stable IDs such as:

```text
planet:Sun
aspect:Moon-Neptune
```

Do not store full interpretation content in local storage.

## Styling

Preserve the current visual character:

- deep violet-black background around `#0f0a1a`
- warm gold accent around `#D4A853`
- muted violet secondary text around `#8a7ab0`
- warm off-white primary text around `#e8ddd0`
- rounded bottom-sheet style interpretation dialog
- subtle chart glow
- restrained starfield
- serif display typography paired with a clean sans-serif body

The first Lovable rebuild should prioritize visual fidelity over a redesign.

## Accessibility requirements

The legacy prototype is touch-first but not fully accessible. The rebuild should improve this without changing the visual identity.

Required:

- all hotspots reachable by keyboard
- hotspots have readable labels
- popup is a semantic dialog
- focus moves into the dialog and returns to the triggering hotspot
- Escape closes the dialog
- reduced-motion preference disables or substantially reduces star animation and slide animation
- buttons have clear focus states
- progress is understandable without relying only on color

## PWA

PWA support is secondary to getting the application architecture correct.

If PWA support is retained:

- generate a valid manifest from assets that actually exist
- avoid hard-coded cache lists that reference missing files
- use the framework's recommended production service-worker approach where possible
- version caches deliberately

Do not copy the legacy service worker unchanged.

## Astrology calculations

Do not bundle the Python calculation stack into the browser application.

For the first migration:

- use the verified static natal profile
- use `karin-chart.svg`
- optionally use the generated `transit-cache.json`

For future dynamic charts or user-entered birth data, create a server-side calculation boundary rather than putting sensitive or heavy calculation logic in client code.

## Testing priorities

At minimum add tests for:

- zodiac sign index mapping, especially Pisces/Fische = 11
- discovery IDs and persistence
- summary unlock threshold
- duplicate discoveries not increasing progress
- aspect lookup
- chart data schema validation

## Legacy files

The following are migration inputs, not architecture templates:

- `index.html`
- `sw.js`
- `manifest.webmanifest`
- `caelus-bundle.js`

Do not reproduce their file organization merely to maintain superficial similarity.
